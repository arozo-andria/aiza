# AIZA

Voice-first MVP for the Sahara CodeSwitch Africa Challenge demo: speak (or type) a
Malagasy/French administrative question, get a transcript, and get back either a
verified, sourced procedure or an honest "I don't have that yet" — never a guess.

## Stack

- Next.js 16 (App Router) + TypeScript, plain CSS (no UI framework)
- Hand-written PWA shell: `public/manifest.json` + `public/sw.js`
- SQLite database (`lib/db.ts`, Node's built-in `node:sqlite`) for the
  knowledge base - see "Knowledge base" below
- `benchmark/` - separate Python benchmark comparing Sahara against 2 other
  speech models on real MG/FR code-switched audio (challenge requirement;
  not part of the deployed app - see `benchmark/README.md`)

## Run it

```bash
npm install
npm run dev
```

Open http://localhost:3000. The text fallback works immediately with no
configuration - try the placeholder example, then try something unrelated
(e.g. "bonjour") to see the honest not-matched state.

## Voice transcription (Sahara)

Copy `.env.example` to `.env.local` and fill in your Intron Sahara build-access key:

```bash
cp .env.example .env.local
```

```
STT_PROVIDER=sahara
SAHARA_API_KEY=<your key>
SAHARA_API_URL=https://infer.voice.intron.io/file/v1/upload/sync
SAHARA_ASR_LANGUAGE=fr
```

Without a key, tapping the mic still records and calls the API, but the app
shows a friendly "not configured" error and points the user at the text
fallback instead of crashing - see `app/api/transcribe/route.ts`.

Note: Malagasy ("mg") isn't in Sahara's published language list, so this
defaults to French ("fr") for the MG/FR code-switched input and shows
whatever Sahara actually transcribes, raw and unedited, on screen. That's
deliberate - the pitch is about benchmarking Sahara honestly, not hiding its
limitations.

**Choice of STT engine is a config seam, not a lock-in**, but the shipped
product deliberately only uses Sahara - the challenge's own guidance is
that the product/demo should be built on Sahara, with the required 3-model
comparison done separately (see `benchmark/`). `STT_PROVIDER` in
`.env.local` selects the engine; only `sahara` is registered in
`app/api/transcribe/route.ts` today. That file's comment documents what was
investigated as other candidates (and why two of the original four
candidates turned out not to be usable) so the reasoning isn't lost.

## Knowledge base

Persisted in SQLite (`lib/db.ts`, `data/aiza.db`), not hardcoded objects.
An entry is either a `ProcedureEntry` (documents/steps/cost/location, like
the shipped `lost_cin` entry) or an `AdviceEntry` (freeform MG/FR advice
text) - both carry `keywords` (for matching) and a `history` table so
verifying an entry again later is an appended row, not an overwrite.
`lib/knowledgeBase.ts` now holds only the types + `SEED_ENTRIES` (used to
seed an empty DB on first run); the DB is the source of truth after that.

Matching runs server-side (`app/api/match/route.ts` → `lib/matchIntent.ts`)
since `node:sqlite` can't run in the browser - the client (`AizaApp.tsx`)
calls that route instead of matching locally. `matchIntent()` itself is
still dead-simple accent-insensitive keyword matching across every DB
entry's `keywords` - intentionally not ML, with a comment marking it as the
seam to swap in a real NLU/LLM classifier later.

The DB opens **read-only** whenever `data/aiza.db` already exists (i.e. in
every deployment, since the pre-seeded file ships with the app) and only
opens read-write to bootstrap+seed a fresh file locally - Vercel's
serverless filesystem is read-only outside `/tmp`, so this avoids a runtime
crash rather than discovering it after deploying. A real "add a procedure
from the app" admin flow would need a hosted DB (Turso/LibSQL, Postgres,
...) instead of a bundled file - noted, not built, given the timeline.

## PWA / installability

- `npm run build && npm run start` runs a real production build - the
  service worker (`public/sw.js`) only registers in production, so use this
  (not `npm run dev`) to test "Add to Home Screen" / run Lighthouse's PWA
  check.
- The service worker is network-first (always fetches fresh, caches only as
  an offline fallback) specifically so a redeploy is never masked by a stale
  cached shell.
- Icons are placeholder art generated by `npm run generate-icons` (a
  dependency-free script that hand-encodes PNGs - see
  `scripts/generate-icons.js`). Swap `public/icons/icon-192.png` and
  `icon-512.png` for real brand art when there's time.

## Deploy to Vercel

```bash
vercel login   # if not already logged in
vercel --prod
```

Then in the Vercel project's dashboard, add the same env vars as
`.env.local` (Settings → Environment Variables) and redeploy so the
production build picks them up.

Make sure `data/aiza.db` exists (run `npm run dev` locally once first if
not - see "Knowledge base") and is not gitignored before deploying, so the
pre-seeded DB actually ships in the bundle instead of the app hitting a
read-only filesystem with no data on first request.

## Before recording the demo video

1. Open the deployed URL on the phone you're recording with, in Chrome.
2. Confirm "Add to Home Screen" is offered (or install via the browser menu).
3. Run through: typed CIN example (matched), typed unrelated text
   (not-matched), then the mic (voice - transcript shows raw even if rough).
